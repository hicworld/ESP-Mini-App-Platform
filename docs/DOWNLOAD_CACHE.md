# HTTPS 应用下载缓存

## 目标

平台 0.3.0 把 HTTPS 应用包下载改为 NAND 上的事务。网络数据不再直接累积到一块下载缓冲区：固件每次读取 2 KiB，写入 `/nand/download/app.part`，同时增量计算完整包 SHA-256。这降低了下载阶段的连续内存压力，并为网络失败、满盘和重启恢复提供明确的清理边界。

商店目录 `index.json` 仍是小文件，继续使用内存下载。应用包完成 NAND 事务后，目前仍会整体载入内存，交给已有的签名、Manifest、WASM 哈希和安装事务校验。因此本阶段完成的是下载落盘与恢复，不是零拷贝验签。

## 提交顺序

1. 开始前删除上一事务的 `app.part` 与 `app.ready`。
2. 根据 HTTP `Content-Length` 和 NAND 剩余容量拒绝无界或明显超限的请求。
3. 仅接受严格 HTTPS、有效证书、HTTP 200 与完整响应。
4. 每块数据先写 `app.part`，再累计长度和 SHA-256；商店安装还会核对索引中的包大小和完整包哈希。
5. 收到精确字节数后执行 `fflush`、`fsync`、`fclose`，再把 `app.part` 原子改名为 `app.ready`。
6. 读取 `app.ready` 进入原有包验签与安装流程，随后删除两个缓存文件。

任一步失败都会关闭句柄并删除两个路径。启动挂载 NAND 后也会执行恢复清理，因此上次下载中途复位留下的临时文件不会被当作有效应用。

## 观察与验收

串口命令：

```text
cache
```

空闲状态应返回：

```text
DOWNLOAD CACHE part=0 part_bytes=0 ready=0 ready_bytes=0
```

0.3.0 已在开发板上通过腾讯 COS 下载并更新 Snake，索引大小、完整包 SHA-256、包签名和安装事务均成功，随后缓存为空。不存在对象返回错误后，缓存仍为空，三个已安装应用不变；软件重启后状态保持，板上自检 23/23。

主机测试直接对生产 `download_cache.c` 注入打开、短写/满盘、flush、fsync、close 和 rename 失败，并验证中断残留恢复，存储套件合计 37/37。尚未完成真实拔电瞬间、物理 NAND 满盘和长时间网络抖动的硬件故障注入。
